How to use this

  1. Drop an audio file, or click to browse. It's decoded and immediately scored against both AI-music detector models.
  2. Review the analysis panel — detector scores, LUFS, stereo correlation, DC offset, silence, transients, spectral rolloff, metadata found, and the spectrum plot.
  3. Pick which signal-chain tools to run in the right-hand panel. Recommended tools (based on the analysis) are badged; "Select recommended" picks them all at once.
  4. Optionally set an output filename and output format (same as source, WAV, MP3, or FLAC — MP3 offers a VBR-0/CBR-320 quality choice) before processing. The default filename is <original name>_fixed with the correct extension for the chosen format.
  5. Click "Process file." A live log and step-aware progress bar track exactly which step is running; both AI-detector fix steps show live sub-progress (current optimization step, retry attempt, and live score) since these stages can take several minutes.
  6. When done, review the before/after table, what-was-done log, and spectrum overlay (labeled before/after), then A/B the original against the fixed file in the player — both are preloaded and switch instantly with no re-buffering gap. Download either one — filenames follow the name and format that were set.

Why the live percentage during optimization can differ from the log line right after it: the number shown while a step is running (e.g. "step 137/400, live estimate 0.006% AI") is a fast internal approximation, checked every step so it can update live. Once that attempt finishes, the actual delivered audio is re-checked against the real detector model - a slower, more thorough check that can land on a noticeably different number (e.g. 3.8%). The fast estimate is a progress signal, not the final answer; only the post-attempt real-model check decides whether the result passes or triggers a retry.

The signal chain, in order

The processing order is deliberate.

  1. Strip metadata & embedded images — reports every tag and any embedded cover art found on the source file, flagging known AI-generation-platform keywords explicitly. Metadata is always stripped from the delivered output regardless of selection (every output is freshly encoded from raw audio) — this step makes that fact visible rather than silent.
  2. Trim leading/trailing silence — true-digital-silence detection (threshold 0.0005 linear amplitude, 5ms safety pad).
  3. DC offset correction — subtracts each channel's mean.
  4. High-pass filter — 4th-order Butterworth, zero-phase, 30Hz cutoff. Runs here, before anything measures level: sub-30Hz rumble inflates the readings the compressor and limiter act on, so it goes first.
  5. Surgical transient/pop fix — detects genuine click/glitch artifacts (requires both a large sample-to-sample jump AND a spike far above a 200ms local RMS envelope, so ordinary kick/snare hits are never flagged) and repairs each by interpolating across it from the clean samples either side. Sustained broadband bursts are rejected: a click crosses the threshold once or twice, a vocal consonant crosses it hundreds of times.
  6. Stereo phase/correlation correction — blends mid/side if correlation is negative enough to risk mono-cancellation. Runs before the high-frequency fill-in so the measurement reads real recorded content rather than synthesised material.
  7. High-frequency spectral fill-in (17kHz+) — detects an artificial hard cutoff (common in lossy encoding or low-quality AI generation) by comparing the actual energy just above a candidate cutoff against what the track's own rolloff slope predicts. Fills content above the cutoff using only this track's own self-fitted rolloff, harmonic projection from its own detected peaks, and texture modulated by its own dynamics — no external reference file anywhere.
  8. Multiband compression — gentle 4-band downward compression (complementary crossovers at 100Hz, 800Hz and 5kHz), ratio 1.3:1, threshold -12dB, one pass, with per-band attack and release. Vocal presence gets its own band rather than sharing with cymbals. Runs before loudness is set, so dynamics are decided at working level.
  9. Temporal pattern denormalization (optional) — applies a small, smooth, non-uniform timing drift, displacing the low-frequency spectral peaks fingerprint matching anchors on. The warp curve is derived from the audio itself, so the same file always produces the same result.
  10. Linear-model AI-detector fix — gradient-based adversarial correction targeting the fakeprint/logistic-regression detector, with live progress reporting during optimization.
  11. CNN-model AI-detector fix — shift-robust gradient optimization targeting the CQT-cepstrum CNN detector, with a slower dense whole-track mode available.
  12. LUFS loudness normalization — default -14 LUFS, adjustable from -16 (Apple Music) to -9 (club/DJ). Second-to-last by design: everything that meaningfully changes level has already run, so the delivered file lands on target instead of drifting off it.
  13. True-peak limiter — brick-wall ceiling at -1dBTP, oversampled 4x to catch inter-sample peaks, with 1.5ms of centred lookahead so gain is already lowered when a peak arrives rather than being yanked down after it.
  14. Post-chain model re-verification (automatic, not a selectable tool) — if both AI fixes were selected, re-scores both models and can run one bounded corrective pass for either model if later processing erased its safety margin.
  15. Post-chain LUFS drift correction (automatic, not a selectable tool) — a safety net rather than the main mechanism, now that loudness is set near the end. If the delivered level still drifts more than 0.1dB from target it is corrected, re-limiting if the correction was upward.

Product watermark: every delivered file receives a fixed, disclosed product mark for aggregate footprint measurement. It is not per-user tracking or DRM. The mark is applied last, never blocks delivery, and is known not to survive 128kbps MP3 or downsampling to 22050Hz and below.

Why AI-detector fixes run after mastering but before the limiter: any gain/EQ/dynamics change applied after an adversarial correction can perturb its exact spectral signature enough to undo it, even if the fix passed real-model verification immediately after it ran. For example, a linear fix verified at under 1% can score much higher again once LUFS normalization or multiband compression runs on top of it. The limiter is the one exception — it's a safety net against clipping, not a musical/spectral-shaping step, and it needs to see the truly final signal to actually guarantee the delivered file stays under its ceiling.

Why there's an automatic re-verification pass: the two detector fixes and the limiter can disturb one another's safety margins. The CNN fix runs first and the cheaper linear fix second; the bounded post-chain sequence checks both models and may retry each once rather than silently trusting an earlier score or ping-ponging indefinitely.

Why LUFS is checked again at the end, for the same reason: it runs mid-chain, but every stage after it can shift overall loudness without anything verifying the final delivered file still matches the target. Traced directly on a real track end-to-end, LUFS held within a fraction of a dB across the whole chain in one full run — but nothing previously guaranteed that on every file, so this exists as the same kind of final safety net the linear-fix re-verification already provided.

Multiband compressor: how it compares to a real one

The concept is standard mastering practice (split into bands, compress each independently to smooth tonal-balance imbalance without one broadband compressor squashing everything together) — real tools like iZotope Ozone, Waves C6, or FabFilter Pro-MB do exactly this. The implementation here is a simplified, conservative version, not a full-featured multiband compressor.

What's missing or simplified compared to a real mastering-grade multiband:

  • Fixed attack/release, not program-dependent. Each band now has its own attack and release (30ms/200ms on the low band through 3ms/60ms on the top), but they are constants. Real compressors vary their release depending on whether they are catching a transient or a sustained passage.
  • No knee. Real compressors have a soft knee — gain reduction ramps in gradually around the threshold rather than switching on hard. This implementation has a hard knee, which can sound more abrupt.
  • No makeup gain. After compressing, real multibands typically add gain back to compensate for the loudness that was removed. This doesn't happen automatically here.
  • No lookahead in the compressor. Its envelope is strictly causal — it reacts to a transient rather than anticipating one. (The true-peak limiter, separately, does look ahead 1.5ms.)
  • Crossovers are zero-phase, not Linkwitz-Riley. The bands are peeled off with zero-phase Butterworth lowpasses and the remainder carried by subtraction, so they sum back to exactly the input. That avoids the level bump independent bandpasses produce, but it is not an LR design, and the split points are nominal rather than -6dB crossover points.

What's genuinely missing (comparing against a real mastering-engineer checklist)

  • Attack/release-aware dynamics (as above) — the biggest gap.
  • Stereo widening/imaging tools beyond the basic phase-correlation fix (mid/side EQ, stereo width control).
  • De-essing (sibilance control) — not applicable to most full mixes but standard on vocal-heavy masters.
  • Harmonic exciter/saturation — a common "analog warmth" step in commercial mastering, not present here.
  • Dithering — out of scope for this version.
  • Reference-track matching (matching tonal curve/loudness to a target reference song) — a common modern mastering workflow, not implemented.
  • Metering/monitoring for mono-fold-down beyond the correlation check — no LRA (loudness range) metering, no true-peak metering displayed pre-limiting.

Verification discipline

Every AI-detector fix is checked against the real (non-differentiable, exact librosa+ONNX pipeline) model, not just the differentiable PyTorch surrogate used during gradient optimization — the surrogate can diverge from the real model specifically after optimization, even when it matches near-perfectly on unperturbed audio. Verification happens during optimization, after resample/stereo transfer, after the full chain, and in the final job result. Step details distinguish a correction being applied from it being verified after transfer; failed verification is surfaced rather than silently relabeled as success.

Roadmap

Fix-interaction correctness (highest priority):

  • The interaction where the CNN fix can disturb the linear fix has a targeted one-shot patch (automatic linear re-verification/retry after the full chain), but the root cause — two independent adversarial corrections sharing the same audio without a joint objective — is unsolved.
  • The CNN whole-track optimizer does not always converge on every overlapping analysis window on long tracks — on one full-track test, 5 of 108 windows plateaued around 93-96% AI probability despite full-budget optimization. This is surfaced in the result (via worst_score_after_transfer/verified_after_transfer) rather than hidden.

Mastering-chain gaps: tonal/corrective EQ, de-essing, harmonic exciter/saturation, stereo widening, glue compression, reference-track matching, fuller metering (loudness range, peak-to-loudness), and compressor refinements (soft knee, makeup gain, program-dependent release).

App/UX gaps: metadata stripping is not a real on/off toggle (every output is always freshly encoded with no tags, so there's no code path where one could survive unchecked); the spectral revival tool's harmonic-projection loop is unvectorized Python (~5x realtime); no undo/versioning across runs, no persistence across server restarts, single-file/single-job workflow only, no authentication/multi-user support (local single-user tool by design).

Deployment

There is no client-side audio processing at all — the frontend is a thin client that calls the Flask backend for every operation. No localStorage, indexedDB, or sessionStorage is used anywhere; nothing persists in the browser. All state lives on the server's disk and in an in-memory job dict that is lost on server restart. Running it requires the Flask server (./run.sh) to be up.
