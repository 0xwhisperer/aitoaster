Documentation

How to use this

  1. Drop an audio file, or click to browse. It's decoded and immediately scored against both AI-music detector models.
  2. Review the analysis panel — detector scores, LUFS, stereo correlation, DC offset, silence, transients, and the spectrum plot.
  3. Pick which signal-chain tools to run in the right-hand panel. Recommended tools (based on the analysis) are badged; "Select recommended" picks them all at once.
  4. Optionally set an output filename before processing — it defaults to <original name>_fixed.wav.
  5. Click "Process file." A live log and step-aware progress bar track exactly which step is running; the CNN fix step also shows its internal optimization step count, since that stage alone can take several minutes.
  6. When done, review the before/after table, what-was-done log, and spectrum overlay, then A/B the original against the fixed file in the player. Download either one — filenames follow the name that was set.

The signal chain, in order

The processing order is deliberate.

  1. Trim leading/trailing silence — true-digital-silence detection (threshold 0.0005 linear amplitude, 5ms safety pad).
  2. DC offset correction — subtracts each channel's mean.
  3. Surgical transient/pop fix — detects genuine click/glitch artifacts (requires both a large sample-to-sample jump AND a spike far above a 200ms local RMS envelope, so ordinary kick/snare hits are never flagged) and applies a raised-cosine gain-reduction envelope (3ms attack, 60ms release). Target reduction is derived from the track's own recent loudness context, not a fixed value.
  4. High-pass filter — 2nd-order Butterworth, zero-phase, 30Hz cutoff.
  5. Stereo phase/correlation correction — blends mid/side if correlation is negative enough to risk mono-cancellation.
  6. LUFS loudness normalization — targets -14 LUFS.
  7. Multiband compression — gentle 3-band downward compression, ratio 1.3:1, threshold -12dB. See limitations below.
  8. Linear-model AI-detector fix — gradient-based adversarial correction targeting the fakeprint/logistic-regression detector.
  9. CNN-model AI-detector fix — whole-track joint gradient optimization targeting the CQT-cepstrum CNN detector across all overlapping 10-second analysis windows simultaneously.
  10. Post-chain linear re-verification (automatic, not a selectable tool) — if both AI fixes were selected, re-scores the linear model on the final post-chain audio and, if the CNN fix disturbed it back above target, re-runs the linear fix once more, verified.
  11. True-peak limiter — brick-wall ceiling at -1dBTP, oversampled 4x to catch inter-sample peaks.

Why AI-detector fixes run after mastering but before the limiter: any gain/EQ/dynamics change applied after an adversarial correction can perturb its exact spectral signature enough to undo it, even if the fix passed real-model verification immediately after it ran. For example, a linear fix verified at under 1% can score much higher again once LUFS normalization or multiband compression runs on top of it. The limiter is the one exception — it's a safety net against clipping, not a musical/spectral-shaping step, and it needs to see the truly final signal to actually guarantee the delivered file stays under its ceiling.

Why there's an automatic re-verification pass: running the linear fix followed by the CNN fix can still let the CNN fix's broadband correction disturb the linear fix's precise correction, even in the correct order. On a full-length test track, a verified 1.56% rose to 9.65% once the CNN fix had also run. The re-verification pass catches and corrects this specific interaction automatically, but is not a complete fix for the underlying issue — see Roadmap.

Multiband compressor: how it compares to a real one

The concept is standard mastering practice (split into bands, compress each independently to smooth tonal-balance imbalance without one broadband compressor squashing everything together) — real tools like iZotope Ozone, Waves C6, or FabFilter Pro-MB do exactly this. The implementation here is a simplified, conservative version, not a full-featured multiband compressor.

What's missing or simplified compared to a real mastering-grade multiband:

  • No attack/release time constants. Real compressors have separate attack and release envelopes (how fast gain reduction engages vs. releases) — this implementation uses a single 20ms median-filter smoothing window as a stand-in for both, which is a crude approximation. A proper compressor would offer attack around 5-30ms and release around 50-500ms independently per band.
  • No knee. Real compressors have a soft knee — gain reduction ramps in gradually around the threshold rather than switching on hard. This implementation has a hard knee, which can sound more abrupt.
  • No makeup gain. After compressing, real multibands typically add gain back to compensate for the loudness that was removed. This doesn't happen automatically here.
  • No lookahead. Cannot anticipate a transient before it hits.
  • Filter crossover isn't phase-aligned/Linkwitz-Riley. Splitting into bands with plain Butterworth low/high/bandpass filters (rather than a proper Linkwitz-Riley crossover) can introduce small phase-cancellation artifacts when the bands are summed back together — professional multiband tools use LR crossovers specifically to avoid this.

What's genuinely missing (comparing against a real mastering-engineer checklist)

  • Attack/release-aware dynamics (as above) — the biggest gap.
  • Stereo widening/imaging tools beyond the basic phase-correlation fix (mid/side EQ, stereo width control).
  • De-essing (sibilance control) — not applicable to most full mixes but standard on vocal-heavy masters.
  • Harmonic exciter/saturation — a common "analog warmth" step in commercial mastering, not present here.
  • Dithering — out of scope for this version.
  • Reference-track matching (matching tonal curve/loudness to a target reference song) — a common modern mastering workflow, not implemented.
  • Metering/monitoring for mono-fold-down beyond the correlation check — no LRA (loudness range) metering, no true-peak metering displayed pre-limiting.

Verification discipline

Every AI-detector fix is checked against the real (non-differentiable, exact librosa+ONNX pipeline) model, not just the differentiable PyTorch surrogate used during gradient optimization — the surrogate can diverge from the real model specifically after optimization, even when it matches near-perfectly on unperturbed audio. Verification happens during optimization (periodic real-score checks with extra optimization weight for windows that disagree), after the resample/stereo transfer (a second, independent point where a verified-good result can still degrade), after the full chain (final linear re-check with automatic retry), and in the final job result (scores always reflect the real model on the actual saved output, never a self-reported mid-pipeline claim). A fix is only ever reported as applied once the real model has confirmed it on the actual delivered audio.

Roadmap

Fix-interaction correctness (highest priority):

  • The interaction where the CNN fix can disturb the linear fix has a targeted one-shot patch (automatic linear re-verification/retry after the full chain), but the root cause — two independent adversarial corrections sharing the same audio without a joint objective — is unsolved.
  • The CNN whole-track optimizer does not always converge on every overlapping analysis window on long tracks — on one full-track test, 5 of 108 windows plateaued around 93-96% AI probability despite full-budget optimization. This is surfaced in the result (via worst_score_after_transfer/verified_after_transfer) rather than hidden.

Mastering-chain gaps: attack/release-aware dynamics, stereo widening/imaging, de-essing, harmonic exciter/saturation, dithering (out of scope), reference-track matching, fuller metering, multiband compressor improvements (attack/release, soft knee, makeup gain, lookahead, Linkwitz-Riley crossovers).

App/UX gaps: no undo/versioning across runs, no persistence across server restarts, single-file/single-job workflow only, no authentication/multi-user support (local single-user tool by design).

Deployment

There is no client-side audio processing at all — the frontend is a thin client that calls the Flask backend for every operation. No localStorage, indexedDB, or sessionStorage is used anywhere; nothing persists in the browser. All state lives on the server's disk and in an in-memory job dict that is lost on server restart. Running it requires the Flask server (./run.sh) to be up.
